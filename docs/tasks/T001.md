## 9. Manifest Requirements (exact)

`manifest.json` at repository root, exactly these keys:

```json
{
  "manifest_version": 3,
  "name": "VEIL",
  "version": "0.1.0",
  "description": "Privacy-first AI browser agent.",
  "minimum_chrome_version": "116",
  "background": {
    "service_worker": "background.js",
    "type": "module"
  },
  "permissions": ["debugger", "offscreen", "storage"],
  "action": {
    "default_title": "VEIL"
  }
}
```

Rules, each with its authority:

1. **`"permissions": ["debugger", "offscreen", "storage"]`** — this is the complete, binding permission set (ADR 010). It is the **minimum** the architecture requires:
   - `debugger` — ADR 002/003 observation and execution via `chrome.debugger`/CDP. Chrome requires this permission declared in the manifest to use the API.
   - `offscreen` — ADR 001: Canvas 2D masking (M08) and WebGPU/WASM local inference (M03, M05) run in an Offscreen Document. Requires the `offscreen` permission (Chrome 109+).
   - `storage` — ADR 007: M10 resolves `$CREDENTIAL_*` tokens from `chrome.storage.local`.
   - **Do not add any other permission.** In particular do **not** add `"<all_urls>"`, any other host permission, `"activeTab"`, `"tabs"`, `"scripting"`, or `"clipboardRead"`. ADR 010 explicitly denies them: VEIL accesses pages through CDP, not through content scripts or host permissions, so those grants would exceed least privilege.
2. **No `host_permissions` key.** ADR 010 denies static host permissions.
3. **No `content_scripts` key.** ADR 002 rejects content-script DOM traversal; CDP is the source of truth.
4. **`"type": "module"`** is required so the bundle loads as an ES module.
5. **No `default_popup`** in this task. The popup task-entry UI is T002's boundary. The `action` key is declared so the extension has an action surface, but T001 delivers no popup HTML. (Runtime context is defined in `ARCHITECTURE.md` §2 Boundary A and `TECH-STACK.md` §2; the task-entry UI is listed as M01 input in `SYSTEM-DESIGN.md` §2 M01 and is implemented with the orchestrator.)
6. **No `web_accessible_resources`** in this task. `offscreen.html` arrives with M08 in T011.
7. **No icons** in this task. No icon asset or path is specified anywhere in the authoritative documents; inventing icon files would violate the zero-guessing rule. The manifest is valid without an `icons` key.

## 10. Build Requirements (exact)

`vite.extension.config.ts` must produce a loadable, unpacked extension in `dist/`. It is a **new, dedicated** file; the root `vite.config.ts` (which serves the React architecture viewer on port 3000) must not be modified:

| Requirement | Value |
|---|---|
| Build entry | `src/m01-core/background.ts` (library mode) |
| Output directory | `dist/` |
| Output filename | `background.js` (single file — the manifest's `service_worker` value) |
| Output format | `es` (ES module) |
| Code splitting | **Disabled.** MV3 service workers must not rely on dynamic chunk loading; emit a single file. |
| `emptyOutDir` | `true` |
| Manifest emission | Copy root `manifest.json` to `dist/manifest.json` during build, via a small inline plugin using Node's `node:fs` — do **not** add a third-party copy plugin dependency. |
| Auxiliary viewer | Must not be built by this config. Do not import `src/main.tsx`, `src/App.tsx`, or `index.html`. |

**Auxiliary-viewer isolation:** `vite.extension.config.ts` must not import `@vitejs/plugin-react`, and must not include `index.html`, `src/main.tsx`, `src/App.tsx`, or `src/index.css` as inputs. The two builds are independent: the viewer keeps `npm run dev` / `npm run build` via `vite.config.ts`; the extension uses `npm run build:extension`.

**Bundle composition contract (`MODULES.md` M01):** `manifest.json` declares one service worker, so all module code is bundled into `background.js`. Vite resolves static imports from other `src/mXX-*/` folders automatically, so M02–M11 code joins the bundle without changing this config. Cross-module data flows only through `INTERFACES.md`; **no module may import `/src/m01-core/` internals.**

**Build command (add to `package.json` scripts, additive):**
- `build:extension` → `vite build --config vite.extension.config.ts`

**devDependencies to add (additive):** `vite`, `vitest`, `jsdom`, `@vitest/coverage-v8`, `typescript`, `@types/chrome`.

Version ranges are resolved by the package manager at implementation time and committed to `package.json`. Do not hand-write version numbers from memory.

**Do not use** `@crxjs/vite-plugin` or any MV3 Vite plugin: the frozen stack names Vite only (`ARCHITECTURE.md` §4), and a plain library build with a manifest copy step satisfies the requirement without adding an unratified dependency.

## 12. Runtime Requirements (exact)

The shell must initialize the extension without performing any perception, reasoning, or execution.

- `src/m01-core/background.ts` — the service worker entry. On load it registers lifecycle listeners and nothing else.
- `src/m01-core/lifecycle.ts` — pure shell logic with these exports:
  - `initializeExtension(): void` — idempotent initialization. Second and later calls are no-ops.
  - `isInitialized(): boolean` — reports initialization state (`false` before `initializeExtension()`, `true` after; stays `true` across repeat calls).
  - `registerLifecycleHandlers(api): void` — registers handlers for `onInstalled` and `onStartup` against a narrow injected API interface, so the logic is testable without Chrome. Registration is idempotent: registering twice must not attach duplicate listeners.
- **Fail-closed:** if registration throws, `initializeExtension` must surface the failure and leave `isInitialized()` returning `false`. It must never report initialized after a failed setup.
- **Service worker dormancy (ADR 001):** do not rely on in-memory state surviving. `initializeExtension` must be safe to call again after the worker restarts.
- **Forbidden here:** any `chrome.debugger` call, any offscreen document creation, any network call, any state machine (T002), any popup UI (T002).

## 13. Failure Behaviour
- Missing/invalid `manifest.json` → load failure; the acceptance check in §11/§14 catches it.
- Invalid permission set (any deviation from §9) → **fail the task**; this is a privacy/least-privilege boundary violation, not a style issue.
- Build emitting files other than `dist/background.js` and `dist/manifest.json` → treat as a build defect (no code splitting, per §10).
- Any thrown error during registration → fail closed per §12; never report a healthy shell.

## 20. Implementation Deviation — Conformance Required

A direct commit to `main` (`fa42f97`) implemented this task while this specification was being ratified. The code is preserved, but it **does not conform** to the decisions ratified here and must be reworked before T001 can be considered complete. The deviation is objective, not stylistic:

| # | Committed `manifest.json` | Binding requirement | Authority |
|---|---|---|---|
| 1 | `host_permissions: ["<all_urls>"]` | **denied** — no host permissions | ADR 010 |
| 2 | `permissions` includes `activeTab` | **not adopted for V1** | ADR 010 |
| 3 | `permissions` includes `scripting` | not required; no content scripts | ADR 010 |
| 4 | `action.default_popup: "index.html"` | popup UI is **T002's** boundary, not T001's; also points the product runtime at the auxiliary viewer's HTML | ADR 001; §9.5; `ARCHITECTURE.md` §1 |
| 5 | `version: "1.0.0"` | shell version `0.1.0` | §9 |
| 6 | (absent) `minimum_chrome_version` | `"116"` required | §9; `ARCHITECTURE.md` §4 |

The committed permission set is a **least-privilege and privacy-boundary violation** (`<all_urls>` grants access VEIL does not use; ADR 010), and `static host permissions` is precisely the grant the architecture avoids by using `chrome.debugger` for observation and execution (ADR 002/003).

Two further conformance points:

- **Build config.** The commit modified the root `vite.config.ts` (adding a manifest-copy plugin and a `background` input alongside the viewer's `index.html`). Per §10 and `MODULES.md` M01, the extension must use a dedicated `vite.extension.config.ts` so the auxiliary viewer's configuration is not repurposed.
- **State machine.** `src/m01-core/stateMachine.ts` uses the correct canonical state set (`docs/agent/STATE-MACHINE.md`, ADR 009) — no competing names. Three transition-table deviations remain to be corrected against that document's §3:
  1. `RECOVERY → IDLE` is accepted; the canonical table permits only `RECOVERY → OBSERVING` and `RECOVERY → ABORTED`.
  2. `RECOVERY` and `ABORTED` are accepted as targets from *any* state, including from the terminal states `COMPLETED`/`ABORTED`; the canonical table permits terminal states to move only to `IDLE`.
  3. `VERIFYING → ABORTED` at three consecutive failures is reached indirectly (via `RECOVERY`); the canonical table allows a direct `VERIFYING → ABORTED`. Confirm this is intended, or implement the direct transition.

**Rework is required to satisfy:** §9 (manifest), §10 (build), §11–§12 (tests/runtime), and `docs/agent/STATE-MACHINE.md`. Until then, T001 is not `VALIDATED`, T002 is not `VALIDATED`, and T003/T004 are not `READY` — their `T001 INTEGRATED` precondition is unmet.
