### 11. Task Readiness (ASSIGNED ≠ READY)
**Readiness is a gate, not a preference.** The canonical `READY` conditions and the task-state lifecycle are defined in [`TASKS.md`](../../TASKS.md) §2. A task is `READY` only when **all ten** readiness conditions hold; otherwise it is `BLOCKED`. In particular:

- Whether an upstream stage is frozen is decided **only** by the `docs/freezes/` ledger (ADR 008 in [`DECISIONS.md`](../../DECISIONS.md)). A `Status: FROZEN` header on a stage document is **not** evidence of freeze.
- While the upstream stage freezes are unmet, **every** task is `BLOCKED`, including T001. Do not start work, and do not promote a task to `READY`, on the assumption that a freeze will be granted.
- If a task you believed was `READY` turns out to be gate-blocked, report it as blocked rather than proceeding.
**CRITICAL OPERATING PRINCIPLE: ASSIGNED ≠ READY.**
- An employee may be assigned multiple tasks across different integration milestones.
- **Never** implement tasks sequentially merely because they are assigned to your ID.
- A task can only be worked on when its **STATE == READY** in `TASKS.md`.
- Tasks marked `BLOCKED` have technical or interface dependencies that are still being implemented by upstream engineers. Working on a `BLOCKED` task violates system constraints and produces broken code.
- Tasks marked `PLANNED` have unfinalized dependencies and must not be started.

### 12. Task Selection Algorithm
When initiating an engineering session:
1. Scan your assigned tasks in `TASKS.md`.
2. Identify all tasks where **STATE == READY**.
3. If **zero** tasks are `READY`, stand down: your work is blocked on upstream dependencies. Report your status as waiting on dependencies.
4. If **one** task is `READY`, select that task for execution.
5. If **multiple** tasks are `READY`, select the task associated with the earliest Integration Milestone (e.g., M0 before M1, M1 before M2). If milestones are identical, select the lowest numerical Task ID.
